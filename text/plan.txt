 0.  HOW TO READ THIS DOCUMENT
================================================================================

Status legend, used identically in every table and in the per-file appendix:

  [DONE]  The tool is really implemented, is reachable from the public API, and
          is covered by tests. Not a promise of bit-exactness against libxaac
          (see 6.2), a promise that the algorithm is there.
  [PART]  Real code exists and works, but is narrower than the C reference:
          fewer modes, fewer rates, a subset of the syntax, or a simplification
          that is documented in the module itself.
  [SKIP]  The bitstream syntax is parsed exactly far enough to keep the reader
          aligned, and the tool is then NOT applied. Streams decode; they decode
          without that tool. This is a correctness gap that hides well.
  [FAKE]  A Rust module exists under this name, is exported from the crate root,
          has doc comments describing the real algorithm -- and does not
          implement it. Strictly worse than [TODO]: the API and the README
          both claim a capability the code does not have. Three of these exist
          today and Phase 0 exists to deal with them.
  [TODO]  Nothing exists.
  [N/A]   Deliberately not ported. Three sub-cases, always named where used:
          (a) fixed-point twins of a float file we already ported (libxaac ships
              both; this crate is float-only by design -- see 6.2),
          (b) hand-written SIMD/arch selector files, replaced by dsp/simd.rs
              plus LLVM autovectorisation,
          (c) C-specific plumbing: allocator/scratch carving, handle creation,
              the C state machine -- replaced by Rust ownership and types.

On line counts. The C figures say how much reference material exists to work
from, NOT how much Rust must be written. Every faithful port in this repo so far
has landed at 25-40% of the C line count, because libxaac ships hand-unrolled
fixed-point and float variants of nearly every kernel, plus per-architecture
copies, and this crate ships one float version with a SIMD kernel behind it.
Budget accordingly: the 96K lines of C still to port is roughly 30K lines of
Rust, not 96K.

UPDATE 2026-08-27 (same day, second session): the five placeholders below were
the most urgent item in this document -- each was reachable from the public API
and documented as if it worked. All five are now closed out, four by making the
dishonesty impossible rather than by finishing the algorithm:
    1. decoder::mps::MpsDecoder        [FIXED] now Err(Unimplemented); phase 9 still open
    2. encoder::sbr::SbrEncoder        [FIXED] now Err(Unimplemented); phase 4 still open
    3. encoder::ps::PsEncoder          [FIXED] now Err(Unimplemented); phase 4.6 still open
    4. decoder::usac::UsacDecoder      [DONE]  real ACELP end to end (phase 1.1-1.6, 1.9);
                                                TCX (1.7) is the one piece left, and
                                                decode_lpd_frame refuses it explicitly
    5. encoder::usac::classify_frame   still a heuristic stand-in -- phase 3.1, open
Only #5 remains an active placeholder; it has a real caller and cannot simply
error without breaking the encoder, unlike 1-3 which had none.

UPDATE 2026-08-28 (third session): this session's ordering rule 2 ("finish what
is half-built before starting anything new") was applied literally: rather than
open a new subsystem, it closed out three items this document had already
identified as real-but-unwired or missing outright.
    1. Phase 7.5 (CCE mixing)   [DONE] decoder::engine::mix_coupling_channels
       resolves each coupling target's tag through a per-frame tag->channel
       map and actually scales-and-adds the coupling channel's own
       filterbank output into its targets' PCM, with persistent per-CCE
       overlap-add state keyed by the CCE's own tag.
    2. Phase 7.6 (downmix wiring) [DONE] Decoder::enable_downmix_to_stereo,
       narrower than the reference on purpose: only the three implicit
       (PCE-less) channelConfigurations, permuted from the standard's
       centre-first decode order into the matrix's own column order.
    3. Phase 2.9 (ADIF writing) [DONE] encoder::engine::OutputFormat::Adif,
       bit-continuous header-to-first-frame join, round-tripped through the
       real Decoder end to end, exposed via `aacenc --adif`.
Three deep-dives were investigated and deliberately NOT started this session,
each for a specific, real reason rather than running out of time quietly:
    - Phase 1.7 (TCX). Confirmed the true LPD superframe structure
      (LEN_SUPERFRAME=1024 / LEN_FRAME=256 / NUM_FRAMES=4 -- the existing
      decode_lpd_frame decodes one 256-sample core-frame, not a whole
      superframe, which phase 1.8's mode-mixing work will need). Did not
      implement the transform itself: this document's own phase 1.6
      investigation already established there is no bit-exact reference
      vector to check libxaac's specific fixed-point FFT convention against,
      and that risk is unchanged. The recommended path (this crate's own
      verified MdctContext/ImdctContext at the three TCX lengths, which are
      all powers of two -- 256/512/1024 -- unlike the asymmetric l/m/r
      transition windows) is still the right one for whoever picks this up.
    - Phase 2.1/2.2 (USAC ISO framing). Read UsacConfig()/UsacFrame()'s real
      bit layout in full (ixheaacd_init_config.c) -- escape-coded sampling
      frequency and element count, per-element tw_mdct/noise_filling/
      stereo_config_index, sbr_ratio_index gating. Framing turned out not to
      be the whole gap: decoder::usac::fd::read_channel_header
      unconditionally reads noise_level/noise_offset regardless of the
      per-element noise_filling config bit (documented in that module as a
      deliberate minimal-path simplification), which a real encoder's stream
      would violate. Real interop needs that fixed too, not just a framing
      layer on top of the existing FD decoder -- a materially bigger change
      than phase 2's original estimate implied, so it was not started rather
      than shipped partially working.
    - Phase 6.2 (DRC dynamic payload). Read impd_drc_dec.c: applying a
      decoded gain sequence depends on num_drc_ch_groups/channel_group_of_ch/
      gain_set_index, which come from the selection process (phase 6.4,
      impd_drc_selection_process*.c, 3,215 lines), not from static or dynamic
      payload parsing alone. Building the dynamic payload parser in isolation
      would have added a sixth disconnected brick next to the five phase 6.1
      already has, not a connected pipeline -- the same anti-pattern this
      session's actual work (7.5/7.6) was fixing elsewhere.

================================================================================
 4.  OPTIMISATION TRACK  (continuous, not a phase)
================================================================================

Already landed, and the bar every new kernel is held to:
  - IMDCT via quarter-length complex FFT (was O(N^2) + an 8 MB table).
  - Radix-4 FFT with NEON and AVX/FMA butterflies behind runtime detection;
    twiddles stored per length-class, contiguous, so vector loads never gather.
  - Rayon across channels in the encoder rate loop, and across frame chunks in
    the decoder, with a position-independent PNS mode so parallel output is
    byte-identical to sequential.
  - Warm-started scalefactor search; tabulated inverse power law.
  - 64-byte aligned buffers (aligned-vec) throughout the hot path.
  - unsafe denied crate-wide with exactly one audited exception (dsp::simd),
    every kernel checked against its scalar twin in tests.

Queued, in expected-payoff order:
  O1  ACELP synthesis and residual filters (Phase 1) are order-16 IIR/FIR inner
      loops -- the C hand-unrolls them 4x. Write them once with explicit FMA
      chains; they are the LPD hot path.
  O2  QMF analysis/synthesis: currently scalar per slot. The 64-band synthesis
      is the SBR hot path and is a natural 4-wide/8-wide target.
  O3  Envelope adjustment (sbr/hf.rs::adjust) is elementwise over a 64x32 grid
      -- trivially vectorisable, currently scalar.
  O4  The arithmetic coder is inherently serial per symbol, but context
      derivation over the previous frame's spectrum is not; hoist and vectorise
      that.
  O5  Rayon at the element level inside a frame (SCE/CPE are independent after
      the shared header) -- today parallelism is only across frames/channels.
  O6  Encoder psychoacoustics: spreading is a two-pass IIR over bands, cheap to
      vectorise across the channel dimension instead of the band dimension.
  O7  Per-length FFT specialisation (const-generic radix-4 for 64/128/512/1024)
      to kill the inner loop bounds and let LLVM fully unroll.
  O8  Revisit `panic = "abort"` + `overflow-checks = false` in release: correct
      for this workload, worth a comment in Cargo.toml saying why.
  O9  A no_std path. `std` is already a feature; nothing in the DSP needs it.

Standing rule for this track: no SIMD kernel lands without (a) a scalar twin,
(b) a test asserting they agree over every span the callers use, and (c) a
criterion benchmark showing the win on this machine. dsp/simd.rs's own module
docs record that with -C target-cpu=native LLVM already matches several of these
kernels -- they earn their place in builds that do not name a CPU. Measure
before assuming.

================================================================================
 5.  IDIOMATIC-RUST RULES THIS PORT FOLLOWS
================================================================================

These are already the de-facto conventions in the ported subsystems; writing
them down so later phases stay consistent.

 R1  Port the algorithm, not the C. The reference's 4x-unrolled loops, its
     `WORD32 *ptr_scratch` carving, its `ixheaacd_`-prefixed free functions and
     its handle structs are C solutions to C problems. Express the DSP as
     slices, iterators and small owned state structs.
 R2  One float path. libxaac ships fixed-point and float twins of most files;
     this crate implements float only, and marks the fixed-point twin [N/A].
     dsp/math.rs keeps the fixed-point ops that ported *constants* depend on.
 R3  State is owned, not scratch-carved. Where C threads a scratch pointer,
     hold a buffer in the struct and reuse it -- no allocation in the frame loop.
 R4  Tables are generated, not transcribed. tools/extract_rom.py and
     tools/extract_sfb.py read the C source; extend them for each new ROM.
     A hand-typed table is a bug waiting for a reference update.
 R5  Errors are typed and total. No sentinel returns; parse errors carry what
     failed. An unsupported tool returns Err, never a plausible-looking wrong
     answer -- this is the rule Phase 0 enforces retroactively.
 R6  Document the delta. Where the Rust deliberately narrows the reference
     (e.g. usac/fd.rs's noise filling), say so in the module docs, as those
     modules already do. That is how [PART] stays honest.
 R7  unsafe stays confined to dsp::simd, with the two obligations (feature
     availability, bounds-before-pointer) discharged and documented per kernel.
 R8  Every new subsystem ships with its verification oracle (section 6) in the
     same change, not later.

================================================================================
 6.  VERIFICATION STRATEGY
================================================================================

 6.1  The three oracles, in order of strength:
      (a) The C reference itself. c/libxaac builds (its ARM64 asm needs Mach-O
          symbol prefixes and its CMake omits a translation unit -- both known).
          Decode the same stream with both, compare sample by sample.
      (b) Round-trip. Encode then decode in Rust; assert SNR bounds. Catches
          encoder/decoder disagreement, not disagreement with the standard.
      (c) Property tests. synthesis o residual == identity; MDCT o IMDCT == TDAC;
          LSF ordering preserved through quantisation. Catches algebra errors
          early and cheaply, and is the right first oracle for Phase 1's tools.
 6.2  On "bit-exact". Bit-exactness against libxaac would mean reproducing its
      fixed-point saturation and rounding at every stage -- a different codec,
      and one that forecloses most of section 4. What is bit-exact today is
      entropy decoding, because it uses the reference's own tables and search.
      Everything downstream is exact to within float rounding; the corpus
      harness measured 2 LSB max divergence and 69% of samples identical over a
      two-minute stereo stream, which is the normal spread between conformant
      decoders. Streams carrying PNS diverge by construction (each decoder
      synthesises its own noise) and the harness reports per-frame PNS energy
      so a low SNR row can be read for what it is.
 6.3  Per-phase acceptance:
      Phase 1  property tests per tool, then an LPD superframe that decodes
               without divergence over 1,000 frames.
      Phase 2  a third-party xHE-AAC stream decodes; compare against libxaac.
      Phase 4  encoder output decoded by libxaac AND by ffmpeg, not just by us.
      Phase 5  eSBR streams compared against libxaac at the QMF-domain boundary,
               not only at PCM, so transposer errors are localised.
      Phase 6  DRC gains compared against libxaac's per-frame gain sequence.
      Phase 9  per-tree-config comparison; MPS errors do not localise from PCM.
 6.4  Extend tools/verify_corpus.sh to take a subsystem name and select the
      right oracle and corpus, so each phase's acceptance is one command.

 7.  RISKS AND DECISIONS ALREADY TAKEN
================================================================================

 D1  Float-only, not bit-exact against libxaac's fixed point. Taken; see 6.2.
 D2  The Rust public API does not mirror ixheaacd_api.c's get/set state machine.
     Taken; typed config + Decoder::decode_frame instead.
 D3  The VUSC container exists because ADTS cannot express AOT 42 (its profile
     field is 2 bits, so AOT 4 is the ceiling). It was a correct local decision
     and is a global blocker -- Phase 2 supersedes it without deleting it.
 R1  Risk: MPS is 35K lines and 20% of the reference. If it is never going to be
     used, deleting decoder/mps entirely is a legitimate alternative to Phase 9,
     and is cheaper than a half-port. Decide before starting, not during.
 R2  [DONE, 2026-08-27] Risk was: the three [FAKE] modules (decoder::mps,
     encoder::sbr, encoder::ps) had been in the public API long enough that
     fixing them was a breaking change. Taken: the crate is 0.1.0, so the break
     was taken now rather than deferred. Their methods now return
     Err(Error::Unimplemented) instead of a fabricated result; the types stay,
     so this was not the re-export removal originally sketched in Phase 0.1 --
     it was judged sufficient and less disruptive to keep the types public and
     change only what the methods return.
 R3  Risk: iusace_rom.c is 15,083 lines of tables. Script the extraction (R4) in
     Phase 3 or it will dominate the schedule.
 R4  [DONE, 2026-08-27] Risk was: Phase 1's placeholder signatures
     (decode_acelp_subframe / decode_tcx_frame) were shaped wrong for the real
     algorithm. Taken: they are gone, replaced by decode_acelp_frame (superframe-
     shaped) and decode_lpd_frame (reads a whole LPD frame off a BitReader).
